全绿不等于对：AI 写代码的 5 条硬规矩

Mr.Sun2026年10月22日...大约 9 分钟AI 实践AI Coding测试变异测试代码审查团队协作

我在一个塔防游戏项目上用 AI 写代码，跑了 8 个月。到昨天为止的账是：

数量
测试用例2249 条（73 个文件）
守卫252 个
变异用例141 个
工程规则53 条
提交294 次
完成的 story30 个

数字摆在这儿，挺好看的。

然后我往状态文件里塞了 113 行复盘。9 条断言，一条没红。

那 113 行占了整个文件的 66%。文件里明明写着「运行复盘不属于本文件，最多留一行指针」——它自己没照做，而守它的守卫全程沉默。

这次事故让我想明白一件事：用 AI 写代码，差距不在你让它写多少、写多快，差在它知不知道自己写对了。 上面那 5 个数字，没有一个能回答这个问题。

下面 5 条是我这 8 个月踩出来的硬规矩。每一条都配一次真实事故。

规矩一：判据要能咬住它要防的那个违规

写完一条断言，问自己一句：违规的时候，它真的会红吗？

我见过 5 类「永远绿」的判据。挑最狠的两个说。

① 断言允许的那件事，正是它要防的那件事

expect(errors.length).toBeLessThanOrEqual(1)

这条断言想防「错误条数超过 1」。但它允许 1，而 1 恰好就是它要防的违规。永远绿。

② 切分前提与真实代码的书写风格不符

这条是代价最大的一次，Story 1.19 的第七轮评审抓到的。

判据长这样——按 ; 把函数体切成「语句」，逐段查相位守卫：

const statements = fnBody.split(';')
expect(statements.some(s => s.includes('phase.kind'))).toBe(true)

而真实实现里，几个 return 之间一个分号都没有。切出来只有一块，于是「读题面的那条语句里有相位判定」恒真。

变异把 === 改成 !== 之后：26 条行为用例全红，唯独这条判据纹丝不动。

26 条红是信号。这条绿是信号之外的信号——而它长得跟「守卫无效」一模一样。

修法不是把切分做得更聪明，是改成白名单：交出题面的那个表达式必须逐字是 phase.question。

判据失效的五类

  1. 上限类断言，允许值 = 违规值
  2. as 向下转型，unknown as Card 编译得过，Card 退化成 any 也过得
  3. 过滤器按「解析前」的值写，但 join 会把 ../../../../ 归一化掉
  4. toThrow() 被另一个函数的抛出满足（G144 断言题单空时抛错，结果 assertInvariants 抓到 null 题面时也抛 ⇒ 变异把题单搞空、它根本没抛，断言照样绿）
  5. 切分前提与真实书写风格不符（上面那个 26 红案例）

这五类都通过了 review，都在全绿的测试套件里活着。没有一个是读代码能一眼看出来的。

规矩二：全绿不是证据，改坏了变红才是

每条守卫写完，必须把被守卫的代码改坏，确认它变红，再复原。

四步都要做：

  1. 改坏被守卫的那一行
  2. grep 证实变异确实落上了
  3. 确认用例变红
  4. 复原，并复核 git diff --stat 与变异前逐字一致

第 2 步为什么不能省

grep 证实变异落盘，测试却 0 红。

我踩过一次：sed 变异按 4 空格匹配，而目标行是 2 空格 ⇒ 变异根本没落上。跑出「48 条全绿」的假象。

不 grep 的话，「全绿」有两种完全相反的解释：

  • 守卫无效
  • 变异没生效

结论完全相反，而输出长得一模一样。

我还漏了第 0 步

项目里大量用 ?raw 导入读组件源码：

import qc from '../../src/components/quiz/QuestionCard.vue?raw'

?raw 的转换结果被 Vite 缓存在 node_modules/.vite。改了 .vue 之后不清理缓存，测试读到的还是变更前那份源码 ⇒ 判据读旧源码 ⇒ 变异「全绿」。

所以跑变异验证之前要先：

rm -rf node_modules/.vite && npx vitest run <file>

清缓存证明「测试读到的是改后的那份」，grep 证明「磁盘上改了」。两步都做，结论才成立。

这个项目到今天为止抓到 4 次假绿/假红

形态各不相同：

  • 变异没落盘（sed 空格数对不上）
  • 变异打在了不会被执行到的那一行（continue 提前吃掉）
  • 测试根本没读到改坏的那份文件（Vite 缓存）
  • 断言被错误的理由满足（toThrow() 被别的函数满足）

这 4 次的共同点：输出都是「0 红」。 如果没有「改坏」这个动作，它们会一直绿下去。

规矩三：守卫的盲区就是你的盲区

上面那个 113 行的故事，根因不在守卫写错了，在守卫量错了地方。

那条守卫的逻辑是：

const start = lines.findIndex((l) => l.startsWith('development_status:'))
const offenders = lines.slice(start).filter((x) => /^\s*#/.test(x.text))
expect(offenders.length).toBeLessThanOrEqual(4)

它量的是 development_status: 块及其之后。而那 113 行复盘挂在 last_updated: 后面，在它上面。

守卫没量到的地方，就是它的盲区。而复盘可以从任何位置灌进来。

改法只有一句话：守卫的测量范围，必须是违规点能出现的位置的超集。

改成「从 last_updated: 行到文件末尾的注释行 ≤ 6」，然后真改文件验了一次——塞 20 行复盘进去，守卫报红：

last_updated 之后已有 24 行注释（上限 6）：
  第 53 行 # 复盘第 1 行：实测值、裁决理由、假绿复盘、工具纪律痕迹…

这条守卫自己迭代了四版才咬得住。 前三版分别是：

版本量法漏在哪
一全文件注释总量 ≤ 60塞 16 行复盘实测 53 < 60，全绿放行
二development_status 块 ≤ 8塞 6 行复盘仍绿
三development_status 块 ≤ 4塞 3 行复盘即红——但复盘改从上面灌进来，就又漏了
四last_updated → EOF ≤ 6✅

四版都写在规则的「守卫」字段里，不是写给后人看的历史，是每次改动都得重读的现役约束。

顺带说一句，量全文件是不行的：文件里有 48 行是 BMAD 生成的静态结构头，工具升级会重新生成它，量全文件等于让守卫在升级时假红。排除静态头的办法是内容锚定，不是行号。

规矩四：判据只能有一份，编号就是契约

复制链是错误的温床

同一段实测值在两个地方维护，改一处忘一处就产生两个真相。

我们的一条规则原文只允许存在于 docs/rules/ 里，另有一道守卫专门查「规则正文有没有第二份」。这条守卫自己也被绕过一次——它靠扫目录判断，于是有 4 条规则的正文被抄到了别处，它照样绿。

后来加了一条自检：把解析器静默失效的情形构造出来，断言它必须红。 一条守卫如果不测「自己会不会失效」，那它只是一段代码，不是一道防线。

编号是承诺

252 个守卫、141 个变异，编号一路排到 G261。规则要求：

  • 守卫 / 变异编号必须接续既有号段，不许乱插
  • 开工前先全仓 uniq -d 查重号
  • 真撞号了，走裁决，留痕

有一次查重实测出 10 个重号，9 个是假警报，唯一真撞的 G30 早于当前 story。这 10 个重号是自己查出来的，不是被别人发现的。

编号一旦有了对外承诺，就不能随便改。我们有一条规则专门管这个：改判据不许为了让守卫变绿而松阈值。理由被实测推翻过的守卫，得改判据并留痕，不能悄悄放宽。

规矩五：欠账要落纸，收尾要贴真输出

「发现问题」有两种处理方式，都不算完

要么当场修，要么登记到 deferred-work.md，写清恢复条件。

不处理是最糟的第三种。这个项目的欠账台账现在 3517 行 / 276KB。听起来吓人，但它是一张能排序、能追责、能交接的清单，不是遗漏。

台账里的一条长这样：

第 25 条：守卫编号纪律缺失 —— 根因是 R-50..R-61 那一段没有规定起号流程
恢复条件：补一条起号规则

它把「我知道了」变成了「别人也能查」。

收尾门槛要贴真实输出

「应该会绿」不算数。每条守卫的收尾都要贴命令的真实输出：

test 2249 全绿（73 文件）
typecheck 零输出
lint 0 error / 1 既有 warning
check-execution-drift.py 无漂移

这四行不是仪式。 它是三个月后有人问「这玩意儿当时到底跑没跑过」时唯一能查的东西。

评审这件事，AI 干得比人细

代码评审我用三层并行：盲审（只看 diff，无上下文）、边界猎手（diff + 项目只读）、验收审计（对照 AC）。

有一轮三层返回 50 条发现，其中 4 条是我判定的假阳性——主评审逐条做变异实测和独立复算，把假阳性驳回并附上证据。

假阳性的驳回记录比真发现更值钱：它写清了「为什么这个发现不成立」，下次没人会重复踩。

落地顺序

如果你也想给 AI 加一道验收信号，我建议这个顺序：

第一步，先写判据，再写实现。
让 AI 写代码之前，先让它写「这段代码怎么算写对了」的判据。判据写不出来，说明需求本身没想清楚。

第二步，每条判据配一次「改坏」。
写完立刻把被守卫的代码改坏一次，看它红不红。红不了，这条判据现在就是装饰品。

第三步，给守卫本身做一次「盲区体检」。
问一句：违规的东西能出现在哪些位置？ 我的测量范围覆盖了全部吗？

第四步，把「发现问题」和「改完」分开记账。
当场修 or 登记台账，二选一，没有第三种。

第五步，规则和编号都当成对外承诺。
一条判据只有一份正文；一个编号一旦发出去就带着承诺，改动要留痕。

这 5 条里，没有一条是关于「怎么写代码」的，全是关于怎么知道代码写对了。

用 AI 写代码的速度上限是模型和上下文决定的，但质量下限是判据决定的。两个团队用同一个模型、同一套工具，一天下来产出差不多——差的全是那些没人验证过的地方：测试绿了但守卫是摆设，变异验证只做了个形式，评审的发现没人复核。

AI 负责生成，人负责兜底。 兜底的具体形态，就是上面这 5 条。
