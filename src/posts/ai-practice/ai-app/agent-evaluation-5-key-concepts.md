# Agent 测评 5 个关键概念：从 LLM 评估到 Multi-Agent 评测体系

> 接 [Phoenix + AI Agent 行为监控](https://sunrong.site/posts/ai-practice/ai-app/ai-agent-phoenix-behavior-monitoring.html)：那篇讲"怎么用 Phoenix 看 Agent 调用"——**本篇讲"为什么 Agent 测评比 LLM 测评难 10 倍" + **5 大测评维度 + Multi-Agent 评测体系**。从 NL2API/NL2SQL/NL2CODE → 记忆 → 规划 → Multi-Agent 协作 → 实战实践。

<!-- more -->

> **TL;DR**：Agent 智能体评估是"对自主 AI 工作流的性能评估"——**表面上与传统 LLM 评估相似，实则有 4 大本质差异**（架构复杂性 / 工具使用 / 自主性 / 推理框架）。**评测必须分两层**：端到端（黑箱）+ 组件级（子 Agent / RAG / API）。**5 大测评维度**：工具能力（NL2API/NL2SQL/NL2CODE）、记忆（短/长）、规划（COT/ReAct）、Multi-Agent 协作、长期记忆 RAG。**Multi-Agent 协作** 比单 Agent 性能高 90.2%（Anthropic 数据）——**通过并行处理扩展"算力"和"思考容量"**。

## 一、Agent 测评 vs LLM 测评：4 大本质差异

| 维度 | LLM 评估 | Agent 智能体评估 |
|---|---|---|
| **架构** | 单模型 | 多组件复杂流程 |
| **工具使用** | 无 | 外部 API / SQL / 代码 |
| **自主性** | 单轮问答 | 自主决定下一步 |
| **推理框架** | 直接回答 | 规划 + 决策策略 |

**核心差异**：**Agent 是"工作流"**——**组件间有复杂交互**——**评估难度大幅提升**——**绝对不能忽视这些组件间的交互**。

## 二、测评的两层架构

```
Agent 智能体评估
│
├── 1. 端到端评估（黑箱视角）
│   └─ 整个系统视为黑箱 → 特定输入下任务是否成功完成
│
└── 2. 组件级评估（白箱视角）
    ├─ 子 Agent
    ├─ RAG（检索增强）
    └─ API 工具调用
```

**两层互补**：
- **端到端** = 验证"任务完成度"
- **组件级** = 定位"故障/瓶颈"

**实战建议**：**先端到端跑通**——**再组件级定位**——**不要一上来就组件级**——**会被细节淹没**。

## 三、多智能体系统（Multi-Agent）总览

### 3.1 定义

**由多个异构或同构智能体组成的协作网络**——**通过分布式决策与任务分解**——**解决单一智能体难以处理的复杂问题**。

### 3.2 3 大核心价值

| 价值 | 含义 | 实战体现 |
|---|---|---|
| **模块化** | 独立智能体降低系统复杂度，便于维护 | 单个 agent 升级不影响其他 |
| **专业化** | 领域专家智能体提升任务精度 | 数学 agent / 搜索 agent 各司其职 |
| **鲁棒性** | 局部故障不影响全局系统 | 一个 agent 失败 = 其他接手 |

### 3.3 Anthropic 关键数据

> **一个由 Claude Opus 4 担任"领导"，多个 Claude Sonnet 4 作为"员工"的多智能体系统，性能比单独使用的 Opus 4 高出 90.2%！**

**背后的逻辑**：
- **Token 使用量本身就解释了 80% 的性能差异**
- **多智能体架构通过并行处理**——**让多个 AI 智能体同时在各自上下文中思考和搜索**
- 本质上是扩展了解决问题的"**算力**"和"**思考容量**"
- 特别适合需要"**广度优先**"探索的复杂问题

### 3.4 典型架构

**目前尚无统一标准范式**——**业界和学界主要以业务驱动设计**——**适用于特定场景的方案**。

## 四、5 大测评维度（核心内容）

### 🎯 维度 1：工具能力测评

| 类型 | 核心能力 | 评测重点 |
|---|---|---|
| **NL2API** | 自然语言转 API 调用 | 意图分类 / API 选择 / 参数提取 / JSON 校验 |
| **NL2SQL** | 自然语言转 SQL 查询 | SQL 语法 / 意图分类 / 多表 join / 查询准确率 |
| **NL2CODE** | 代码生成 / 续写 / 解释 | 正确性 / 性能效率 / 鲁棒性 / 安全性 |

**为什么 3 个并列？**——**这是 Agent 调用外部世界的 3 大接口**：
- **NL2API** = 通用业务接口
- **NL2SQL** = 数据库接口
- **NL2CODE** = 编程接口

**实战建议**：
- 每个 NL2X 任务**至少准备 50+ 测试用例**
- 包含**正常 + 边界 + 异常** 3 类
- 评测时**记录"调用了哪个 API/库"**——**不要只看最终结果**

### 🧠 维度 2：记忆能力测评

| 类型 | 存储方式 | 评测要点 |
|---|---|---|
| **短期记忆** | Token 上下文 | 多轮对话上下文识别 / 信息补全 / 主题切换 |
| **长期记忆** | 向量知识库 + RAG | 检索召回率 / 生成准确率 / 回答相关性 |

**短期记忆的关键挑战**：
- **Token 窗口有限**（128K / 200K）——**超长对话必须压缩**
- **主题切换 = 信息丢失**——**多轮上下文识别**是难点
- [W6 段 3 详细讲过 context 压缩 + 双 Ratio + 3 层回退](/posts/ai-practice/ai-app/agentscope-w6-memory-and-context.html)

**长期记忆（RAG）的关键指标**：
- **检索召回率** = 找到正确答案的概率
- **生成准确率** = 答案正确的概率
- **回答相关性** = 答案对应问题的程度

**实战建议**：
- 短期记忆**准备"多轮注入"测试**——看 N 轮前的信息还能不能记住
- 长期记忆**准备"注入-检索"对照测试**——注入 100 条，查询"X 是什么"

### 🧭 维度 3：规划能力测评

| 技术 | 原理 | 评测指标 |
|---|---|---|
| **COT（思维链）** | 显式输出中间推理步骤 | 答案准确率 / 步骤合理性 / 错误传播率 |
| **ReAct（推理+行动）** | 推理 + 行动框架 | 任务完成率 / 工具调用准确率 / Token 效率 |

**COT 的关键评估**：
- **步骤合理性** = 每步推理是否符合逻辑
- **错误传播率** = 错一步 → 后面对多少步（决定要不要加自检）
- **步骤数 vs 准确率** 曲线——**步骤少但错** vs **步骤多但对** 的 trade-off

**ReAct 的关键评估**：
- **任务完成率** = 端到端能完成多少
- **工具调用准确率** = 调对工具的概率
- **Token 效率** = 完成同样任务用多少 token

**AgentScope 实战**：**ReAct 是 Agent 核心**——W2 我深读 `_acting_impl` + `_reasoning_impl`——**这是 W2 Q5 提交 Issue #2166 的来源**。

### 🤝 维度 4：Multi-Agent 协作能力

**3 大评测维度**：

| 维度 | 评测什么 |
|---|---|
| **任务理解一致性** | 术语对齐 / 本体匹配（多 agent 理解是否一致）|
| **动态协调可靠性** | 时钟同步 / 状态同步（消息不丢失不重复）|
| **上下文鲁棒性** | 对抗样本 / 语义噪声（一个 agent 出错不影响其他）|

**实战测试方法**：
```python
# 测试 1: 一致性
agents_process_same_query()  # 多 agent 答案是否一致

# 测试 2: 协调可靠性
disable_one_agent()  # 看其他 agent 是否能继续

# 测试 3: 鲁棒性
inject_noisy_input()  # 看是否会传染到其他 agent
```

### 📚 维度 5：长期记忆 RAG 评测

**详细见 W6 + Phoenix blog**——**这里给核心指标**：

```
RAG 评测 = 检索质量 + 生成质量
           ↓              ↓
        召回率         准确性
        精确率         相关性
        MRR            Faithfulness
        NDCG           Answer Relevance
```

**详细评测方法见 [Phoenix + AI Agent 行为监控 Level 2-3](https://sunrong.site/posts/ai-practice/ai-app/ai-agent-phoenix-behavior-monitoring.html)**。

## 五、典型测评实践

### 实践 1：智能排障 Agent

**场景**：网络故障工单处理

**涉及**：
- 意图识别（"网络不通" = ping 测试 / DNS 检查 / 路由检查？）
- 工具调用（ping 工具 / 路由工具 / 知识库工具）
- RAG 知识问答（"某型号路由器常见故障"）

**评测**：
- 端到端：工单处理成功率 / 平均处理时长
- 组件级：意图识别准确率 / 工具调用准确率 / RAG 召回率

### 实践 2：优化 Agent（E2E 闭环）

```
问题识别 → 定界定位 → 方案生成 → 效果评估
   ↓          ↓          ↓          ↓
  评测 1    评测 2     评测 3     评测 4
```

**4 阶段 4 评测**：
- 评测 1：问题识别准确率
- 评测 2：定界定位准确率（范围/位置对吗）
- 评测 3：方案生成可行性
- 评测 4：效果评估（实际执行后是否解决）

**关键**：**4 个评测不是孤立的**——**前 3 个错了 = 第 4 个一定错**。

## 八、5 大 Agent 测评原则

### 1. **端到端 + 组件级双管齐下**

不要只测一个层面——**黑箱测通过 + 白箱找问题**——**两者互补**。

### 2. **真实数据 > 合成数据**

评测集**尽量用真实业务数据**——**合成数据容易过拟合**——**真实数据才能反映真实表现**。

### 3. **自动化 + 人工评估结合**

- **自动化** = 量、客观、可重复
- **人工评估** = 质、主观、case by case

**两者结合才能完整**。

### 4. **持续评测，不要一次性**

Agent 是持续演化的——**评测集要跟着更新**——**避免"老评测集过拟合"**。

### 5. **评测 = 优化的镜子**

**不要为了评测而评测**——**每次评测结果要驱动 1-2 个优化动作**——**否则评测无意义**。
