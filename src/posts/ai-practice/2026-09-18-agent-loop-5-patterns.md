## 💎 观点 1:Agent Loop 的 4 阶段循环

```
[感知] → [思考] → [行动] → [反馈]
   ↑                          │
   └──────────────────────────┘
        (反馈作为下一轮感知)
```

### 1.1 4 阶段详解

| 阶段 | 输入 | 输出 | 实现 |
| :--- | :--- | :--- | :--- |
| **感知** | 用户指令 / 环境状态 | 当前上下文 | 读取消息 / RAG 检索 / Tool 结果 |
| **思考** | 感知结果 | 决策(下一步 / 结束) | LLM 推理 |
| **行动** | 思考结果 | 调用结果 | 外部 API / Tool / 数据库 |
| **反馈** | 行动结果 | 新感知信息 | 结果解析 / 异常处理 / 日志 |

### 1.2 与人类思维类比

| Agent Loop | 人类思维 | 例子 |
| :--- | :--- | :--- |
| **感知** | "老板让我写个 PPT" | 听指令 |
| **思考** | "先列大纲,再写每页" | 思考策略 |
| **行动** | "打开 PowerPoint 开始写" | 动手做 |
| **反馈** | "第一页写完了,继续下一页" | 自我检查 |
| **再次感知** | "第一页内容不够好,要改" | 重新评估 |

**关键洞察**:**Agent Loop = 人类认知的工程化实现**。一次循环 = 一次完整思考。

### 1.3 Agent Loop 是 Agent 的运行引擎

```
Agent = Harness + Model
AgentLoop = Agent 的"心脏"(运行机制)
```

- 没有 AgentLoop → Model 只是个问答机器
- 没有 Harness → AgentLoop 跑起来也没用(失控)
- **AgentLoop 是"Model 跟外部世界怎么对话"**

## 💎 观点 2:Agent Loop 的 5 大核心组件

### 2.1 5 组件总览

```
┌─────────────────────────────────────────┐
│           Agent Loop 核心                │
│  ┌──────────┐   ┌──────────┐           │
│  │ ① 状态管理 │ ←→│ ② 决策引擎 │ ← (核心)   │
│  └──────────┘   └──────────┘           │
│  ┌──────────┐   ┌──────────┐           │
│  │ ③ 工具执行 │ ←→│ ④ 记忆模块 │           │
│  └──────────┘   └──────────┘           │
│       ↓                                   │
│  ┌──────────┐                            │
│  │ ⑤ 终止校验 │                            │
│  └──────────┘                            │
└─────────────────────────────────────────┘
```

### 2.2 5 组件详解

| # | 组件 | 作用 | 关键挑战 | 失败会怎样 |
| :--- | :--- | :--- | :--- | :--- |
| ① | **状态管理器** | 维护对话 / 任务 / 流程状态 | 状态一致性 / 序列化 | 状态错乱 |
| ② | **决策引擎**(核心) | 决定下一步动作 | 上下文完整 / 推理正确 | 跑偏 / 卡死 |
| ③ | **工具执行器** | 调用外部 API / 数据库 / 文件 | 参数正确 / 异常处理 | Tool 调用失败 |
| ④ | **记忆模块** | 短期 + 长期记忆 | 短期压缩 / 长异步持久 | 失忆 / 重复问 |
| ⑤ | **终止校验器** | 判断"该结束了" | 成功条件 / 最大轮次 | 无限循环 |

### 2.3 核心原理

> **"AgentLoop 的本质 = 上下文驱动的状态延续。"**

**含义**:
- Agent 没有"自身状态",**只有"context + tool"**
- 每一轮的状态 = 之前的 context + tool 调用历史
- "延续"靠 context 拼接(ReAct)或显式状态存储(Plan/反思)

## 💎 观点 3:5 大主流 AgentLoop

### 3.1 总览表

| # | 模式 | 复杂度 | 轮次 | 核心思想 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **基础工具调用** | ⭐ | 1-3 | LLM 直接调函数 | 简单查询 / 操作 |
| 2 | **ReAct** | ⭐⭐ | 中 | **迭代规划调整** | 动态任务 / 通用 |
| 3 | **Plan-and-Execute** | ⭐⭐⭐ | 长 | **全局规划** | 长程复杂 / 流程明确 |
| 4 | **反思迭代** | ⭐⭐⭐ | 长 | **执行 → 反思 → 修正** | 高容错 / 代码审查 |
| 5 | **多智能体协作** | ⭐⭐⭐⭐⭐ | 长 | 跨领域涌现 | 跨领域极高复杂度 |

### 3.2 模式 1:基础工具调用(1-3 轮)

最简单的模式:LLM 直接调函数。

```
User: "查一下今天天气"
LLM: 调 weather_api
LLM: 回复 "今天 25 度,晴"
```

**适用**:简单查询 / 操作 / ChatGPT Function Calling / 大部分场景。

### 3.3 模式 2:ReAct(迭代规划调整)

**ReAct = Reasoning + Acting**(思考 + 行动交替)

```
[思考] 思考下一步
   ↓
[行动] 调用工具
   ↓
[观察] 拿到结果
   ↓
回到 [思考]
```

**核心机制**:**上下文拼接实现记忆延续**——所有历史堆到 context 里。

```python
# ReAct 伪代码
context = []
while not done:
    thought = llm.think(context)
    context.append({"role": "assistant", "content": thought})
    
    tool, args = llm.decide_action(thought)
    result = execute_tool(tool, args)
    
    observation = f"Tool {tool} returned: {result}"
    context.append({"role": "user", "content": observation})
    
    done = llm.is_done(thought)
```

**优缺点**:

| 优点 | 缺点 |
| :--- | :--- |
| **动态性好**——每步根据最新结果调整 | **长任务目标容易漂移** |
| **通用性好**——适用各种任务 | **缺全局视野**(只看眼前) |
| **实现简单**——上下文堆就行 | **Token 消耗增加较快** |

**类比**:**下棋——想一步走一步**。

### 3.4 模式 3:Plan-and-Execute(全局规划)

**先计划,再执行**——默认人的思维模式。

```
[Plan] 规划整体任务
   ↓
[Execute] 逐步执行(每步可以是 ReAct)
   ↓
[Re-Plan] 必要时调整计划
   ↓
[Execute] 继续执行
```

**核心思想**:**任务拆解 = 任务降维**。

**优缺点**:

| 优点 | 缺点 |
| :--- | :--- |
| **稳定性强**——有全局计划,不会跑偏 | **计划错了后面全错** |
| **适合长任务**——任务明确时好分解 | **初期规划成本高** |
| **目标清晰**——用户能看清楚整个计划 | **不灵活** |

**类比**:**写代码——先设计再写**。

### 3.5 ReAct vs Plan-and-Execute 核心区分

| 维度 | ReAct | Plan-and-Execute |
| :--- | :--- | :--- |
| **本质** | **迭代规划调整** | **全局规划** |
| **稳定** | ⭐⭐ | ⭐⭐⭐⭐ |
| **灵活** | ⭐⭐⭐⭐ | ⭐⭐ |
| **类比** | 下棋 | 写代码 |

**最佳实践**:**ReAct + Plan 混合 = 防漂移的标准组合**——先用 Plan 定目标,再用 ReAct 做执行。

### 3.6 模式 4:反思迭代(执行 → 反思 → 修正)

```
[执行] 完成一个动作
   ↓
[反思] 检查结果
   ↓
[修正] 如果不行,重做
   ↓
回到 [执行]
```

**三层反思**(关键结构):

| 层次 | 反思什么 | 谁来做 |
| :--- | :--- | :--- |
| **结果校验层** | 这次执行的结果对吗? | 自动(代码 / 测试) |
| **过程复盘层** | 这次的执行过程合理吗? | LLM |
| **策略优化层** | 整体策略要调整吗? | LLM + 人类(关键决策) |

**优缺点**:

| 优点 | 缺点 |
| :--- | :--- |
| **幻觉少**(多层校验) | **Token 消耗量很大** |
| **鲁棒性强**(自我纠错) | **响应慢**(多轮反思) |
| **质量稳定** | **可能反思错误**(LLM 也可能错) |

**适用场景**:代码审查、法律文书、医疗诊断、金融决策。

**类比**:**写论文——写完反复改**。

### 3.7 模式 5:多智能体协作(慎用)

| 子模式 | 结构 | 协调方式 | 适用场景 |
| :--- | :--- | :--- | :--- |
| **主从模式** | Orchestrator + SubAgent | Orchestrator 调度 | 任务明确、需要问责 |
| **对等协商** | 平级 Agent | 投票 / 协商 / 互相 review | 探索性、需要涌现 |

| 维度 | 评价 |
| :--- | :--- |
| **优点** | 跨领域 + 高复杂度 / 涌现 / 鲁棒 |
| **缺点** | **稳定性较低** / **Token 消耗极高** / **速度很慢** |

**适用场景**:开发全流程、头脑风暴、跨领域极高复杂度任务。

> **"多智能体协作是 5 大循环中成本最高的——慎用。"**

### 3.8 5 大循环对比

| 维度 | 基础工具调用 | ReAct | Plan-and-Execute | 反思迭代 | 多智能体协作 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **响应速度** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐ | ⭐ | ⭐ |
| **稳定性** | ⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| **Token 消耗** | 低 | 中 | 低 | **极高** | **极高** |
| **容错能力** | ⭐⭐ | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| **可解释性** | ⭐ | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| **适用复杂度** | 单步 | 中 | 高 | 高 | 极高 |

## 💎 观点 4:Agent Loop 的 4 大痛点 + 双重保险

### 4.1 双重终止保险(鲁棒性核心)

| 维度 | 任务完成 | 异常状态 |
| :--- | :--- | :--- |
| **触发条件** | LLM 判断"做完了" | 超时 / 错误 / 异常 |
| **动作** | 优雅退出 | **强制停止** + 错误返回 |
| **关键作用** | 正常完成 | 防止无限循环 / 资源耗尽 |

**关键洞察**:**"双重保险"是 AgentLoop 鲁棒性的核心**——没有它,Agent 跑飞了都不知道。

### 4.2 4 大痛点 + 防御

#### 痛点 1:无限循环

| 措施 | 作用 | 配置 |
| :--- | :--- | :--- |
| **最大迭代次数** | 硬性终止 | `max_iters = 10-20` |
| **超时时间** | 时间维度硬性终止 | `timeout = 60s` |
| **进度检测** | 没进展就停 | "同一状态重复 N 次" |
| **异常终止** | 出错就停 | Tool 失败率 > 50% |

> **"无限循环 = AgentLoop 的'心脏病';双重保险是'心脏起搏器'。"**

#### 痛点 2:目标漂移

| 措施 | 作用 |
| :--- | :--- |
| **Plan-and-Execute** | 提前固化目标 |
| **定期 Re-Plan** | 每 N 轮回顾"我现在还在主线吗?" |
| **用户 Confirm** | 关键节点用户确认 |

> **"目标漂移 = AgentLoop 的'阿尔茨海默';规划是'指南针'。"**

#### 痛点 3:上下文溢出

| 措施 | 作用 |
| :--- | :--- |
| **关键信息压缩** | LLM 做摘要 |
| **下沉长期记忆** | 老的对话存到 PG / Mem0 |
| **滑动窗口** | 只保留最近 N 轮 |
| **结构化状态** | 不存对话,存结构化数据 |

> **"上下文溢出 = AgentLoop 的'记忆饱和';压缩 + 下沉是'大脑'。"**

#### 痛点 4:性能瓶颈

| 优化 | 作用 | 收益 |
| :--- | :--- | :--- |
| **Prompt 缓存** | 同样 prompt 不重复算 | 50%+ 加速 |
| **Tool 调用缓存** | 同样 tool 不重复调 | 30%+ 加速 |
| **并行执行** | 不依赖的 tool 并发调 | 2-5x 加速 |
| **模型分层** | 简单任务用小模型 | 成本 80%+ |

> **"性能瓶颈 = AgentLoop 的'动脉硬化';缓存是'血管支架'。"**

### 4.3 痛点的元规则

> **"AgentLoop 的所有痛点,本质都是'无限资源约束下做有限任务'。"**
> **"防御不是'避免',是'提前知道怎么停'。"**

***

## 💎 观点 5:loop 模式的选择 — 5 大原则

### 5.1 4 维度判断

| 维度 | 选项 |
| :--- | :--- |
| **复杂度** | 单步 / 多步 |
| **问题确定性** | 固定 / 动态 |
| **质量要求** | 低 / 高 |
| **协作需求** | 单 Agent / 多 Agent |

### 5.2 完整决策树

```
任务复杂度?
├─ 单步 → 基础工具调用(LLM + 1 个 Tool,直接出结果)
│
├─ 多步:
│   ├─ 问题固定 / 目标清晰?
│   │   ├─ 是 → Plan-and-Execute(稳定 + 可解释)
│   │   └─ 否 → ReAct(动态探索)
│   │
│   ├─ 高质量要求(代码 / 法律 / 医疗)?
│   │   └─ 是 → 反思迭代(鲁棒 + 多层校验)
│   │
│   └─ 需要多领域协作 / 涌现?
│       └─ 是 → 多智能体协作(成本高,慎用)
```

### 5.3 5 大选择原则

| # | 原则 | 含义 |
| --- | --- | --- |
| 1 | **够用原则** | 不选最复杂的,选能满足需求的 |
| 2 | **成本匹配** | Token 消耗要跟任务价值匹配 |
| 3 | **渐进升级** | 先简单,出问题再升级 |
| 4 | **可控优化** | **可控和稳定性最优先** |
| 5 | **场景适配** | 没有最好,只有最合适 |

### 5.4 元洞察

> **"90% 的场景,ReAct + Plan-and-Execute 混合就够了"** —— 不需要上一上多智能体。
>
> **"先跑起来,再迭代"** —— 跟昨天的"Harness 是迭代出来的"呼应。

***

## 📌 总结:Agent Loop 5 大模式的 3 句话

1. **本质**:**Agent Loop = 上下文驱动的状态延续**,5 大核心组件构成最小可行 Agent。
2. **选择**:**90% 场景用 ReAct + Plan 混合**;代码审查用反思迭代;跨领域用多智能体(慎用)。
3. **运维**:**双重保险 + 4 大防御** 让 Agent 不跑飞。

***

## 💬 最后一句话

> **"Agent Loop 5 大模式,5 种思维模式。**"
>
> **"ReAct 像下棋,Plan 像写代码,反思像写论文,多智能体像交响乐,基础调用像点菜。**"
>
> **"没有最好的 loop,只有最合适的 loop。"**

跟昨天(9-17)讲的"Harness 是迭代出来的"呼应——**Agent Loop 模式不是一开始就要选对,是先跑起来再迭代**。
