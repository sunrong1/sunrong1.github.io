# 知识工程系列（3 篇）

> 企业真正需要的不是"能查资料的 AI"，而是**持续演化的知识工程体系**。

## 🧭 核心脉络

```
RAG 遇到的问题                    LLM Wiki 的回答
─────────────────────────────────────────────────────
重检索而无关联        →          关系在编译时就建好了
碎片化无整体感        →          架构总览是一等公民
无法形成长期记忆      →          wiki 是持续累积的产物
被动膨胀（只进不出）  →          lint 让过时和矛盾可见
─────────────────────────────────────────────────────
                    关键位移
              检索发生在「查询时」→ 知识发生在「编译时」
```

***
## 💡 三条核心判断

1. **三个命题里第三条决定生死** — Agent 需要什么知识 / 如何组织 / 如何持续更新。
   前两件决定效果，**第三件决定生死**：一次性搭好的知识库，三个月后是垃圾场。

2. **关系密度比复用率更关键** — 回答一个问题需要读几个源文件？
   1 个 → RAG；10+ 个且不读全就答不对 → **必须 Wiki**。
   因为 RAG 每次只捞几个 chunk，这是结构上的天花板。

3. **"为什么"的知识只有 Wiki 存得下** — 「为什么用 PostgreSQL 而不是 MySQL」
   这个答案分散在 PR 讨论、ADR 和某人的脑子里。
   RAG 检索到一段，答出来的是任意的；**Wiki 里有一篇专讲这件事**。

**三条路线解同一个问题（怎么让 Agent 用好知识），但切入点不同：**

| 路线 | 切入点 | 适合谁先看 |
|---|---|---|
| **RAG 范式演进** | 在检索层做加法 | 想调优现有 RAG 的 |
| **Agentic RAG** | 把 RAG 本身 Agent 化 | 想让 Agent 自己决定检索什么 |
| **LLM Wiki** | 换掉知识形态 | 知识稳定、需要长期沉淀的 |
