# RAG 还是 LLM Wiki：一张决策表帮你选对知识方案

> **这不是"新旧替代"，是两种知识生命周期。**
>
> 选错的代价不是效果差一点，是**方向性地错**。

<!-- more -->

这是[知识工程系列](/posts/ai-practice/ai-theory/knowledge-engineering-llm-wiki.html)的第 2 篇。

上一篇讲了 LLM Wiki 是什么、怎么分层、三个引擎怎么转。这篇解决一个更实际的问题：

> **我手上这个问题，到底该上 RAG，还是该上 LLM Wiki？**

---

## 一、先破一个误解

很多人以为这是"先进 vs 落后"：

```
RAG（2020 年的东西）  ←→  LLM Wiki（2026 年的东西）
```

**不是。** 这两者解决的是**知识生命周期的两个不同阶段**。

| | RAG | LLM Wiki |
|---|---|---|
| **知识形态** | 原始片段 | 结构化页面 |
| **工作时机** | **查询时** | **编译时** |
| **知识寿命** | 每次查询重新推导 | 持续累积 |
| **适合** | 一次性 / 变化快 / 无结构 | 长期沉淀 / 高频复用 / 强结构 |

> ⭐ **一句话判断：**
>
> **这份知识，你会不会问第二次？**
>
> 会问第二次 → 它值得被编译。
> 不会 → 直接 RAG，别折腾。

## 二、真实的失败模式

### 失败模式 A：在 RAG 上过度投入

**症状**：向量库调了三个月，chunk size 试了 8 种，加了 reranker，加了 query rewrite，**效果还是不稳定**。

**根因**：**你在优化"检索"，但问题出在"知识没有结构"。**

分块再聪明，捞出来的还是碎片。模型拿到的是：

```
"timeout 默认 30s"（来自 config.py）
"调用前检查 timeout 参数"（来自 api.py）
"超时抛 TimeoutError"（来自 client.py）
```

**三句话都在，但"为什么是 30s"这个知识不在。** 因为它是**跨文件的推论**，从来没被写下来过。

> **RAG 的能力上限 = 原始资料里已经显式写出来的东西。**
>
> 资料里没有的，检索一万次也检索不出来。

### 失败模式 B：在 LLM Wiki 上过度投入

**症状**：wiki 建了 200 页，架构图画得漂亮，**但没人用**。Agent 还在重读源码。

**根因**：三个常见 ——

| 症状 | 真因 |
|---|---|
| 编译完就不更新了 | 没有 lint 机制，三个月后 wiki 是负资产 |
| 页面越建越多，检索反而变差 | 没做模块化隔离，索引已经撑不住 |
| Agent 不用 wiki，直接读源码 | **wiki 里没有它当前任务需要的那条知识** |

最后一条最隐蔽，也最容易误判成"工具不好用"。

> ⭐ **LLM Wiki 的失败模式是"建了但不维护"，RAG 的失败模式是"维护了但没结构"。**
>
> **两者都需要工程投入，只是投入的方向不同。**

## 三、决策表

### 主决策路径

```
你的知识会被反复问吗？
    │
    ├── 不会（一次性任务 / 临时分析）──→ RAG，甚至直接塞进上下文
    │
    └── 会
        │
        知识之间有强关系（代码架构 / 业务模型 / 决策链）？
            │
            ├── 有 ──→ LLM Wiki
            │
            └── 没有（独立 FAQ / 独立文档）
                    │
                    知识更新频率高吗？
                        │
                        ├── 高（每天变）──→ RAG
                        └── 低 ──→ 看规模
                                │
                                ├── < 100 篇 ──→ RAG + 简单索引就够
                                └── 大规模 / 需治理 ──→ LLM Wiki
```

### 速查表

| 场景 | 推荐 | 理由 |
|---|---|---|
| **代码库问答**（"认证怎么实现的"）| **LLM Wiki** | 强关系、跨文件、需要长期累积 |
| **产品文档问答**（"XX 功能怎么用"）| RAG | 独立文档、更新频繁 |
| **客服 FAQ** | RAG | 每条独立、变化快 |
| **论文库 / 竞品研究** | **LLM Wiki** | 长期积累、需要交叉引用和矛盾追踪 |
| **个人知识库** | **LLM Wiki** | Karpathy 原始场景，复利效应最强 |
| **临时分析一堆资料** | RAG | 问完就丢，编译成本不划算 |
| **团队规范 / 最佳实践沉淀** | **LLM Wiki** | 需要"为什么这么定"和冲突检测 |
| **企业内部制度查询** | 看治理需求 | 制度常变 → RAG；要能追溯"哪版生效" → Wiki |

## 四、三个判断维度

### ① 复用率：这个问题会被问几次？

最直接的指标。

```
被问 1 次   → RAG（编译成本 > 收益）
被问 2-3 次 → 边缘，看其他维度
被问 5 次+  → LLM Wiki
```

**为什么"编译"有盈亏平衡点？**

因为编译有成本：写 AGENTS.md 规范、设计页面结构、跑 lint、**每次新原料还要有人在场盯着摄入**。

Karpathy 自己都说，摄入时他倾向**一份一份来并且全程参与** —— 这就是成本。

> ⭐ **别高估复利。**
>
> 复利的前提是"持续问"。问三次的知识，编译它不如直接问三次。

### ② 关系密度：知识之间有多强的耦合？

**这是最容易被忽略、也最关键的维度。**

| 关系密度 | 例子 | 适合 |
|---|---|---|
| **低**（各自独立）| FAQ、API 文档、常见错误 | RAG |
| **中**（有引用关系）| 设计文档、决策记录 | Wiki 或 GraphRAG |
| **高**（互相依赖）| 代码架构、业务领域模型 | **LLM Wiki** |

**怎么判断？问一句：**

> **"要回答这个问题，我需要读几个源文件？"**
>
> 1 个 → RAG
> 3-5 个，且它们之间有引用 → Wiki
> 10+ 个，且不读全就答不对 → **必须 Wiki**

**因为 RAG 每次都只捞几个 chunk。** 你的问题需要读 10 个文件才答得对，RAG 结构上就答不对。

### ③ 治理需求：知识会不会矛盾、会不会过时？

| 治理需求 | RAG | LLM Wiki |
|---|---|---|
| 文档过时了，希望自动发现 | ❌ 做不到 | ✅ lint 的过时检查 |
| 两份文档矛盾，希望标记 | ❌ 做不到 | ✅ lint 的矛盾检测 |
| 三个月没人用的知识，希望淘汰 | ❌ 做不到 | ✅ 归档 / 淘汰流程 |
| 知识之间有孤岛，需要发现 | ❌ 做不到 | ✅ lint 的孤立页面检查 |

> ⭐ **只要你的知识库里有"文档会过时"这一个问题，RAG 就已经在裸奔。**
>
> 不是效果问题，是**你永远不知道哪条答案是错的**。

## 五、混合方案才是常态

**现实中很少二选一。**

一个团队的知识库通常长这样：

```
                    编译时（Wiki）         查询时（RAG）
                    ─────────────         ──────────
  稳定不变         │  架构决策          │  FAQ
  的知识           │  领域模型          │  API 文档
                   │  代码结构          │  常见错误
                   │  历史决策          │
                   └───────────────────┘
  快速变化         │  规范演进记录      │  产品文档
  的知识           │  （存"为什么改"）  │  团队制度
                   └───────────────────┘
```

**典型分工：**

| 知识类型 | 放哪 | 为什么 |
|---|---|---|
| **"是什么"**（当前事实）| RAG | 更新快，编译成本不划算 |
| **"为什么是这样"**（决策与推理）| **Wiki** | 这是 Wiki 独有的能力，RAG 存不了 |

> ⭐ **这是 LLM Wiki 最不可替代的地方。**
>
> 「为什么当初用 PostgreSQL 而不是 MySQL」——
> 这个答案**分散在几个 PR 讨论、一份 ADR、和某个人的脑子里**。
>
> RAG 检索到其中一段，答出来的可能是任意的。
> **Wiki 里有一篇 `decisions/why-postgres.md` 专门讲这件事。**

## 六、落地路径

### 别一步跳到 Wiki

**推荐节奏：**

```
第 1 阶段：先做最笨的 RAG
  └─ 目的不是效果，是摸清"大家到底在问什么"
  └─ 产出：一份高频问题清单

第 2 阶段：从清单里挑出"被问最多的 20%"
  └─ 这些就是值得编译的
  └─ 人工写 5-10 篇核心页面（不用 LLM 编译，手写质量更高）

第 3 阶段：这时候再上 LLM Wiki 自动化
  └─ 你已经知道"哪些知识值得沉淀"
  └─ AGENTS.md 规范也写得出来（因为你想清楚了）
  └─ 原料就是那 5-10 篇 + 持续新增的资料
```

> ⭐ **为什么第 2 阶段要手写？**
>
> 因为**手写过程本身就是思考过程。**
>
> 你手写一篇 `architecture.md` 的时候，才真正想清楚了这个项目的架构。
> 直接让 LLM 编译一遍，你得到的是一份"看起来很全但你没读过的文档"。
>
> **而且你会立刻发现：值不值得做。** 手写 3 篇就烦了 → 说明你的知识没那么值得沉淀。

### 一个可以立刻试的最小版本

**不用装任何工具，先手工做一次：**

```
1. 挑一个你被反复问的问题域（比如"新同学怎么上手这个项目"）
2. 让 AI 读 10 个关键文件，手写出一篇 onboarding.md
3. 把这篇放进你的 CLAUDE.md 或 AGENTS.md 里
4. 下次新会话，让 Agent 先读这篇
5. 观察：Agent 是不是少问了 3 个问题？
```

**如果答案是"是"，你就有动力继续。** 如果不是，**说明你的问题不在知识层，在别处**。

> **这个 5 步的成本 < 1 小时。** 比调研 5 个 RAG 框架强。

## 七、什么时候两个都别上

| 情况 | 该做什么 |
|---|---|
| **知识在人的脑子里** | 先写文档，别急着上系统 |
| **问题本身是模糊的** | 先把问题定义清楚 |
| **数据源不可靠** | 源头治理优先，检索层救不了脏数据 |
| **需求量太小**（一个月问 2 次）| 直接问人更快 |
| **没有一个人会持续维护** | **别做。** 三个月后一定是垃圾场 |

最后一条我要重复一遍，因为它最常被忽略：

> ⭐ **Karpathy 说人类放弃 wiki 的原因是"维护成本增长得比价值快"。**
>
> LLM 把维护成本压到接近零 —— 但它改变不了"**如果没有人真的去读那个 wiki，它就是负资产**"。
